# Testing PAIR Mission Control (pair-next live stack)

## Stack & startup
- Server: `node scripts/serve-mission-control.mjs` (repo root, built `dist/` — run `pnpm build` first if stale). Port `PAIR_MC_PORT` (default 8788). Serves the built SPA from `apps/mission-control-ui/dist` (falls back to an inline legacy UI if `dist` is missing — check `PAIR Mission Control` page title + React DOM to know which UI you got).
- Env that changes behavior: `PAIR_MC_TOKEN` (auth), `PAIR_DSH_HOME`/`CODEX_HOME` (register DSH/CODEX executors even if they later probe UNQUALIFIED), `PAIR_DEVIN_API_KEY` (DEVIN qualification; remote dispatches burn real ACU — capped by `PAIR_MAX_REMOTE_TASKS_PER_DAY`, default 10), `PAIR_COST_HALT`/`COST_HALT` file (kill-switch).
- State dir `PAIR_MC_DIR`: `pair.db` persists across restarts — projects/missions survive; workspace is a `ws-*` dir under it.
- `scripts/start-pair-live.sh` brings up server + cloudflared tunnel + telegram bridge (bridge needs `PA Pair_TG_BOT_TOKEN`, absent = expected).

## Auth (UI)
- Every `/api/*` requires `Authorization: Bearer $PAIR_MC_TOKEN` (or `?token=` query for SSE).
- The SPA stores the token in `localStorage["pair.mc_token"]`. On **any** 401 it calls `window.prompt("Mission Control access token:")` and reloads on a non-null answer.
- **Gotcha:** the dashboard fires ~4 parallel API calls; each 401 queues its own `prompt()`. Expect to answer the same token prompt up to 4 times (filling each with the real token is harmless; Cancel skips that one). A `type` into the prompt may not land — click the input field first, type, then click OK.
- Fast path for automation: seed `localStorage["pair.mc_token"]` (and `pair.operator_id`, see below) via console/CDP before navigating, skipping the prompt entirely.

## Operator id
- POSTs (`/api/missions`, `/api/missions/preview`, actions) require operator identity: `x-operator-id` header or `operator_id` in body — otherwise the server rejects. The UI sends `x-operator-id` from `localStorage["pair.operator_id"]`, bound to the `#opid` input in the top-right header. Set it before submitting (e.g. `op:e2e`).

## API surface (common mistakes)
- There is **no** `/api/executors`. Executor status lives in `GET /api/routing` (`executors[]` + `routable[]` with gate detail and `reason_not_routable`). `GET /api/health` gives per-subsystem states. Other routes: `/api/missions`, `/api/missions/:id` (+`/dag`,`/timeline`,`/evidence`,`/files`), `/api/missions/preview` (POST, creates nothing), `/api/providers`, `/api/models`, `/api/routes`, `/api/approvals`, `/api/cost`, `/api/schedules`.
- Mission list items use `status`/`runtime_state` (not `state`). Executor `qualification_state` is nested at `descriptor.qualification.state` / `descriptor.metadata.qualification_state`, not top-level — several UI columns read the wrong path and show "—" (known bug, verify against API before trusting the rendered table).

## Mission issue flow & what "healthy" looks like
- `/missions/new`: goal textarea + project select + auto-confirm checkbox (default ON → one-click "Plan & run"; OFF → "Preview plan" review table + plan digest → "Confirm & run"). Server re-checks the plan digest on submit (two-step submit is fail-closed).
- Planner: if no LLM model route qualified at boot (`MODEL_ROUTE: skip ... (not discovered)` in logs), the plan expander no-ops and the **template planner** runs: T1 records the goal on PAIR_NATIVE (writes `mission_goal.txt`), T2 "llm analysis (dsh)" requiring `REASONING`, T3 codex step only if goal mentions code/script/python.
- If DSH is registered but UNQUALIFIED, T2 gets `ROUTING_DECISION_RECORDED → NO_ELIGIBLE_EXECUTOR` → recovery → mission stays `RUNNING` with T2 `READY` forever. That is correct fail-closed behavior, NOT a bug — assert the reason surfaces (mission timeline, Observability → Routing decisions tab) rather than expecting COMPLETED.
- Bare `serve-mission-control.mjs` registers DSH/CODEX only when `PAIR_DSH_HOME`/`CODEX_HOME` are set in its env — `start-pair-live.sh` defaults them to `~/.pair-dsh-home`/`~/.codex`. Launching the serve script directly without them gives 2/2 routable (DEVIN+PAIR_NATIVE) instead of 4/4; set both vars to match the scripted stack.
- PAIR_NATIVE runs locally and writes real artifacts into the mission workspace — verify `mission_goal.txt` both in the UI file viewer and on disk under the project `root_location`.
- DEVIN dispatches create real Devin sessions and spend ACU; avoid unless that's what you're testing (check `/api/cost` remote_dispatches_today first).

## P14-era additions (business layer / work_open_binding)
- **Durable-state boot fragility (FIXED at f6d3fa3 / PR #10):** pre-fix builds crashed on boot when pair.db held REMOVED model entries (`probeModel` threw `FAIL_CLOSED_MODEL_REMOVED` uncaught in the route-qualification loop). Post-fix the loop logs `MODEL_ROUTE: <route> model REMOVED — skipped` and boots normally. To regression-test: `/home/ubuntu/pair-mc-live/pair.db` retains the exact crash state (3 model_entry rows `["REMOVED","STALE"]` streak 3 for all wanted routes + provider rows) — copy it to a scratch PAIR_MC_DIR and boot; pre-fix exits before listening, post-fix serves. `entities` rows are payload-hash-integrity-checked — if hand-seeding, recompute `payload_hash = digest(payload)` via `./dist/pair/canonical.js`.
- **Restart-orphan behavior:** killing the server mid-execution strands the in-flight execution as `UNKNOWN` on restart (the supervisor rehydrates the mission_runtime — PR #10 Defect B — but does NOT auto-retry/re-drive the stranded task; the mission parks RUNNING with no pending recovery). `/api/missions/:id/reconcile` returns a receipt (`CONFIRMED_NOT_EXECUTED`, replay_allowed) but doesn't re-drive. Operator `work-items/:id/cancel` unwinds it cleanly (execution → CANCELLED cancelled_by OPERATOR). Expect this whenever you restart mid-flight — it's a test-harness artifact as much as a product behavior.
- **Node ABI:** better-sqlite3 must match the node major used to run the server — if boot dies with "compiled against a different Node.js version", rebuild in `node_modules/.pnpm/better-sqlite3@*/node_modules/better-sqlite3` via `npm run build-release` with the runtime node on PATH.
- **`?token=` works on every `/api/*` GET** (not just SSE) — handy for showing JSON evidence pages in the browser during recordings (`/api/businesses/:id?token=...`).
- **Business API:** POST `/api/businesses`, `/api/org-agents`, `/api/work-items` (+`:id/open|assign|cancel|claim|block|comment|artifacts`); GET `/api/businesses/:id` returns detail incl. `board` — and `board()` is the trigger that runs `syncWorkItem` for IN_PROGRESS items (terminal fold only fires on a board read, not on `/api/work-items` list). Agent lifecycle: POST `/api/org-agents/:id/pause|resume|terminate` (PAUSED/ACTIVE/TERMINATED) — `/open` on a paused assignee → 409 `FAIL_CLOSED_AGENT_INACTIVE` (ADMISSION gate, fires before binding creation → no residue rows); an already-bound mission keeps resolving under PAUSED (PROVENANCE mode → no quarantine). Fold outcomes by bound-mission terminal state: COMPLETED→DONE, FAILED→BLOCKED (blocked_code stays null — distinct from provenance quarantine), CANCELLED→CANCELLED.
- **Authority model (P14):** `work_open_binding` rows (store `entities` table) are the only mission↔work-item authority: pinned mission_id BEFORE creation, states INTENT→BOUND|ROLLED_BACK. Public POST /api/missions rejects `mission_id` → 409 `FAIL_CLOSED_MISSION_ID_PUBLIC`. Metadata `source:"business_layer"`/`work_item_*` is observability-only — a forged mission still gets a real agent_contract pin but confers zero work-item authority. Verify via sqlite (no GET route for bindings) + `work_item.mission_ids` + `blocked_code`.
- **Fold semantics:** bound mission terminal → `syncWorkItem` folds → work item DONE (requires_review=false); terminal event shows as `WORK_ITEM_SYNCED` on the mission timeline. Second `/open` while the bound mission is live → `FAIL_CLOSED_MISSION_ACTIVE` (governed, expected). POST `/api/work-items/:id/cancel` also exercises the fold (work item → CANCELLED, mission → CANCELLED) — the fallback when an executor's upstream flakes and the mission can't reach COMPLETED. Flaky executor note: DSH ACP turns can hit upstream `503` mid-execution → execution FAILED → recovery retries (RETRY_SAME_ROUTE, WAITING_BACKOFF) → after repeated failures it escalates `HUMAN_APPROVAL_REQUIRED` → mission parks in WAITING_APPROVAL with a pending `APR_*` (governed, not a retry storm). Mission rows carry top-level `bound_open_id` (= binding open_id for bound missions, null for public).
- **Runtime-hardening R1 (PR #10, head 5543581+):** `resume()` only reconstructs `mission_runtime` when `mission.status=="CREATED"` + runtime missing (the provable creation crash window). READY/RUNNING/PAUSED + missing runtime → fail-closed: `restart_blocker{code:"FAIL_CLOSED_RUNTIME_AMBIGUOUS",observed_mission_status}` stamped on `entities` row `mission_recovery_checkpoint`/`MRCP_<msn>` + `MISSION_RUNTIME_AMBIGUOUS` row in the `events` table; NO MRT row, no wake — mission frozen (tasks/executions can't advance). Idempotent across restarts (one extra event per restart, blocker rewritten). To exercise: kill server while mission RUNNING → `DELETE FROM entities WHERE entity_type='mission_runtime' AND entity_id='MRT_<msn>'` → restart. The blocker is NOT exposed via `GET /api/missions/:id` — sqlite/events only (operator visibility gap to report). CREATED window is hittable: kill ~0.4s after `/open` returns (mission stays CREATED before the first tick); deletion+restart then proves the allowed path (runtime reconstructed → mission proceeds normally). Operator cancel on a frozen mission works — creates a transient MRT to drive CANCELLED.
- **UI auth over tunnel:** the SPA sends `Authorization: Bearer <localStorage pair.mc_token>` + `x-operator-id: <pair.operator_id>`. No `?token=` capture — seed both keys via devtools console once on the target origin, or answer the `window.prompt("Mission Control access token:")` dialogs (they queue ~1 per failed concurrent request at first load; after the token sticks they stop). Operator id is also settable via the top-right "operator" input — it persists to the same key.
- **Mission submit paths (PR #18+):** /missions/new — auto-confirm checkbox (default ON, `pair.auto_confirm`) → "Plan & run" chains preview→submit; OFF → "Preview plan" renders task table+DAG+`plan digest:` → "Confirm & run". First LLM plan call ~55-90s ("Planning…" button) — expected, not a hang; confirm resolves the digest-cached plan in ~seconds. POST /api/missions with `confirm_plan.digest` not in cache → 409 FAIL_CLOSED_PLAN_UNKNOWN in ~ms (resolves before expansion). `metadata.pinned_plan` on the mission JSON = server pinned the confirmed plan.
